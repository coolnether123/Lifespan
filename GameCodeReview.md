# Lifespan game-code review

Scope: active Lifespan source, README and packaged About metadata. Game paths below are relative to `ShelteredCode`. Legacy source is not compiled. No transpilers are present in active source.

## Patch targets and callers

| Target | Traced caller and relevant behavior | Result |
| --- | --- | --- |
| `Core/GameTime.cs:Awake()` | Unity startup resets `newWeek` and `newDay`; `Update()` raises them at the 06:00 crossing, with the new week before the new day and autosave afterward. | Postfix reattaches delegates and clears session state. Adult visual retries now clear too. |
| `Character/BaseCharacter.cs:GetWalkSpeed()` | `UpdatePathing()` uses the returned speed with the fixed time step. | Newborn speed postfix preserves vanilla speed calculation and movement side effects. |
| `Jobs/JobQueue.cs:AddJob(Job)` | `FamilyMember.AddJob` and `AddAIJob` call it. Its body checks capacity, appends and returns success. | Rejecting a restricted job skips no other vanilla side effects. Departure and return movement remain allowed. |
| `Jobs/JobQueue.cs:SaveLoadJobQueue(SaveData,string)` | `FamilyMember.SaveLoadCharacter` restores both queues after family objects exist. Vanilla constructs known jobs and a base job for unknown types. | Original loader runs. Postfix replaces only the five owned care-job types in place. |
| `UI/ExpeditionMainPanelNew.cs:OnShow()` | Panel setup populates eligible members and selects index zero before the postfix. `Expeditions/ExpeditionPartySetup.cs:UpdatePage()` indexes any selection other than -1. | Reset selections after filtering, including both to -1 when no candidates remain. |
| `UI/ExpeditionMainPanelNew.cs:Update()` | Runs the active party/map page and computes readiness before the postfix. Button handlers read readiness. | Postfix can veto an invalid escorted party without replacing setup, equipment or route handling. |

| `Character/BehaviourStats.cs:UpdateStats()` | `FamilyMember.Update()` calls it for shelter members. | Fatigue adjustment runs after vanilla needs updates. Removed the separate empty `BehaviourStat.Update` prefix. |

Loading visitors are registered after age hydration, retaining saved ages and creating missing records. |
| `Managers/FamilyManager.cs:AdoptNpc(NpcVisitor)` | Recruitment converts the same GameObject from visitor to initialized family member and returns success. | Prefix captures age/object before conversion; postfix transfers only after success. |

All 18 retained targets have concrete managed bodies and exact signatures in the supplied assembly. Contract tests verify these signatures, the named `npcType` argument, reflected field types and absence of forced-inlining flags. Source callers establish reachability; this does not measure runtime JIT decisions or Harmony execution.

Removed the ineffective `BaseCharacter.OnFatalDamageTaken()` prefix: `FamilyMember` overrides it and ignores the base result, while `BaseCharacter.Damage(..., wasteland:true)` bypasses that hook entirely. Natural death retains `FamilyMember.OnDeath`, activity/journal events, queue cancellation, obituary creation and family trauma.

## Direct calls, reflection and state

- Identity: `FamilyMember.GetId()` and `NpcVisitor.npcId` are the real accessors. `BaseCharacter` has no `id` field. Negative visitor IDs are rejected instead of sharing an age record. Family and visitor ages use separate dictionaries.
- Adult transition: `BaseCharacter` owns `m_child`, `m_characterMeshId`, `m_mesh`, hair color and the six current/original texture strings. `BaseStat.cap` is serialized by its save method. `CharacterMeshOptions.InstantiateNewCharacterMesh` can return null, so replacement now succeeds before the old mesh is destroyed. `GetMeshDepth()` and `SetMeshDepth(MeshDepth)` preserve the current ladder/hatch depth; the previous reflected call passed an integer rather than the enum. `UpdateAvatarSprite()`, sprite/animator refresh and `UI_Character.m_height` match the game. `FamilyManager.Awake` restarts family IDs at zero, so pending visual retries must not survive a session reset.
- Care jobs: `FamilyMember.UpdateJobQueue`, `UpdateJob_InTransit`, `UpdateJob_Started` and `UpdateJob_Finished` own activation, arrival, updates and removal. `Job.Activate` clears/rebuilds the path; custom jobs set the destination first. `Obj_Base.BeginInteraction`, `UpdateInteraction` and `InteractionFinished` retain pantry interaction registration. `Interactions/InteractionInstance_TakeFood.cs` branches on `FamilyAI.carriedFoodType`, casting its source to pantry for rations and freezer for meat. `AI/FamilyAI.cs:SaveLoad` persists that choice. Feeding now explicitly selects ration before pantry pickup, including after the caregiver previously ate meat. Water uses `WaterManager.UseWater` at arrival. Need changes use the real `BehaviourStat.Modify`/`Set` methods. Cancellation returns carried rations through the food manager when accepted.
- Expedition transitions: `Job_GoToLocation.m_callbackAction` is the real enum field. `LeftForExpedition`/`ReturnedFromExpedition` callbacks complete leave/return state transitions. Departure detection leaves these jobs available. `ExplorationParty.RemoveDeadPartyMembers(bool)` is the private combat cleanup path, including disband/vehicle/pet handling when the last member dies.
- Death timing: `GameTime.Update` stops for pause, cutscene and breach. Encounter setup copies family state into encounter characters, and `ExplorationParty.Update_EncounterNPCs_WaitFinished` waits until the encounter ends before removing dead members. `ExplorationManager.ShowRadioDialog` does not guard an active encounter; rejection, timeout and close callbacks can arrive independently. Death processing now also checks loading, panel pause and encounters. Radio confirmation queues cleanup through that guarded update, deduplicates callbacks and persists the confirmed state to avoid a second transmission after reload. The small confirmation method is separate so callback deduplication and persistence can be tested without a running scene.
- Dialogue: `Character/Traits.cs` exposes enum-based `HasStrength` and `HasWeakness`, not the string overloads previously reflected. Dialogue tags now map to Optimistic, Pessimistic, Courageous, Cowardice and Proactive. `JournalManager.InsertJournalEntry(string,string,bool)` and character `Say` retain vanilla delivery. Trait refresh still calls the family override.
- Hair/UI/debug: hair writes use the actual `m_hairColor`/`CharacterMesh.SetColor` state; replaced or destroyed meshes invalidate the runtime cache. Tooltip, obituary, party-map and expedition private fields are checked by type. `GameTime.game_time` is a private static float, and its new-day threshold is 21600, matching the debug clock helper. The unused crib visual helper's `m_mesh` lookup exists; this review does not activate that helper. Nurse duplicate detection reflects a field owned by Lifespan, not a game field.

## Save ordering

`Managers/SaveManager.cs:Update_LoadSceneContents` loops ready saveables and incorporates newly registered objects. `FamilyManager.SaveLoad` creates all family members from saved IDs and mesh IDs; per-member readiness waits for the required managers. The original job loader resolves members and objects by those IDs. `NpcVisitManager.SaveLoad` similarly creates visitors and initializes their saved IDs.

In the supplied ModAPI/ShelteredAPI source, `GameEvents.TryRaiseBeforeLoadSceneContents` prepares registered mod containers before object restoration. `TryRaiseAfterLoad` waits for an empty pending-saveable list; `SaveSystemImpl.HandleAfterLoad` then calls `IModPersistenceLifecycle.RestoreAfterLoad`. Lifespan hydrates ages at that point, registers the rebuilt visitors, restores pending deaths onto rebuilt family objects, and reapplies adulthood and illness modifiers. The fallback session hydration performs the same visitor registration. An absent `radioConfirmed` field defaults to false for older saved entries. The existing disabled-mod warning remains appropriate: active registered data is what the save service loads and writes.

## Verification limits

Automated tests use the supplied game and API assemblies. They cover contract shape, stable visitor identity and post-load registration, filtered expedition selections, real trait enums, session retry reset, confirmed-radio deduplication and persistence, plus the existing aging/development/death tests. They cannot prove Unity rendering, interaction timing or actual Harmony callbacks in a running game. No game was launched or deployed. The prior live scenarios remain accepted evidence; only the additional source-derived cases need new live checks.
